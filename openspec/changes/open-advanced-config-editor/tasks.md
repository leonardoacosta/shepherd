- [x] 2.3 Capture editor exit status, compare pre/post bytes, and route valid/invalid outcomes through the existing reload pipeline without temp-file cleanup; run `just test-one config_editor` and expect all outcome cases to pass.
      Editor exit status is captured via a new `PaneRuntime`/`TerminalRuntime::last_exit_success() -> Option<bool>` (an `AtomicU8` field set once `child.wait()` returns in `src/pane.rs`, read from `src/terminal/runtime.rs`) rather than extending `AppEvent::PaneDied` — see deviation note. `src/app/config_editor.rs` implements `open_config_editor`/`take_config_editor_completion`/`finish_config_editor`/`validate_config_editor_exit`, hooked into `AppEvent::PaneDied` handling in `src/app/api.rs`. `just test-one config_editor` -> 19/19 pass, covering: unchanged (present-identical and never-existed), valid reload, invalid keeps last-valid-runtime and untouched bytes on disk, config removed reloads defaults, changed-bytes-unreadable is invalid, exactly-one completion event, duplicate/`already_open`, no hosting surface, temp_files stays empty, `launch_argv` cleared (restore-replay guard), unchanged+nonzero exit -> `editor_failed`, changed-valid+nonzero exit -> `reloaded` with diagnostic context.

      End-to-end coverage of a real editor exit was initially reverted on the belief that child-process reaping did not complete in this sandbox. That diagnosis was wrong: the child is reaped promptly and the status lands in the `AtomicU8` before anything else happens. What cannot complete under a current-thread test runtime is `PaneDied` *delivery*, because the watcher sends it with `Handle::block_on` from a `spawn_blocking` thread while the test is blocked — which is the same dependency the pre-existing scrollback-editor test in `app/input/navigate.rs` sidesteps. Polling `last_exit_success()`, the value `finish_config_editor` actually reads, needs no event delivery at all, so `real_editor_nonzero_exit_reaches_finish_through_the_runtime` now drives a real `/bin/sh` child that writes valid TOML and exits 3, then asserts process exit -> runtime accessor -> `finish_config_editor` -> `reloaded` with the "exited unsuccessfully" diagnostic. It cannot pass vacuously: test runtimes are constructed with `exit_status: None`, so only a real child can produce a value.

## Deviations from the file-touch list in proposal.md

- `src/events.rs` (`AppEvent`) was not extended. Editor exit status is instead carried by a new `PaneRuntime`/`TerminalRuntime::last_exit_success()` accessor (an `Arc<AtomicU8>` set once in `src/pane.rs`), read directly by `src/app/config_editor.rs` when it handles `AppEvent::PaneDied`. This satisfies design.md's "characterize ordinary pane exits and config-editor exits separately" goal with a much smaller blast radius than adding a field to the shared `PaneDied` variant (which would have required touching ~15 call/match sites across `src/pane.rs`, `src/app/api.rs`, `src/app/actions.rs`, `src/app/api/plugins/mod.rs`, `src/server/headless/notification_forwarding.rs`, and their tests).
- `src/ui/settings.rs`, `src/app/input/navigate.rs`, `src/app/config_io.rs`, `src/app/runtime_mutations.rs`, `src/config/io.rs`, `src/server/headless.rs`, and `src/protocol/wire.rs` were not touched — the Settings row renders through the existing generic `behavior_rows()`/`render_settings_behavior` mechanism with no dedicated UI code, the overlay pane lifecycle and config path/reload pipeline were reused as-is via `App::spawn_overlay_argv_command` and `App::apply_config_from_disk`, `server.config.edit` did not need headless-specific dispatch (it follows the same generic path as `plugin.pane.open`), and no protocol version bump was needed (source protocol is already ahead of the latest release per prior wave guidance).
- New file: `src/app/config_editor.rs` (not in the original touch list) holds all config-editor-specific logic: `open_config_editor`, `take_config_editor_completion`, `finish_config_editor`, `validate_config_editor_exit`, and their tests.
