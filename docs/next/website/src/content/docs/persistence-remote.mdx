title: Persistence and remote access
description: Detach from Shepherd, reattach later, use named sessions, and connect over SSH.

Shepherd keeps panes running in a background server. Your terminal client can detach and reconnect later.

For the local, SSH, and `shepherd --remote` workflows, see [How to work with Shepherd](/docs/how-to-work/).

## Detach and reattach

Detach the client with `ctrl+b q`; panes and agents keep running. Reattach by running `shepherd` again. Stop the session and its panes with `shepherd server stop`.

When Shepherd starts again after a full server stop, it restores the saved session shape. For what survives detach, server restart, screen history replay, native agent session restore, and live handoff, see [Session state and restore](/docs/session-state/).

## Named sessions

Use named sessions when you want independent Shepherd servers.

```bash
shepherd session list
shepherd session attach work
shepherd session attach side-project
shepherd session stop work
shepherd session delete side-project
```

A named session has its own panes, tabs, workspaces, sockets, and runtime state. It still shares the same global config file.

Use `--json` for scripts:

```bash
shepherd session list --json
shepherd session stop work --json
shepherd session delete side-project --json
```

## Remote attach over SSH

There are two remote modes; [How to work with Shepherd](/docs/how-to-work/) compares them. SSH to the server and run `shepherd` there for the tmux-style path. Or attach through SSH from your local machine:

```bash
shepherd --remote workbox
shepherd --remote ssh://you@server:2222
```

In this mode your local Shepherd is a thin client. It connects over SSH, starts or attaches to the remote Shepherd server, and streams the UI back to your local terminal. Because the client runs locally, Shepherd can bridge local desktop features such as image clipboard paste into the remote session by copying the image to a remote temp file and pasting that path.

By default, `shepherd --remote` uses your local Shepherd keybindings for that attach. This keeps local muscle memory even when the remote server has different config. The local keybindings are a snapshot from attach time; detach and reattach after editing local keybindings. Use `--remote-keybindings server` when you want the remote server config instead. Local custom command keybindings are not sent, because those commands would run on the remote host.

For repeat targets, use your SSH config:

```text
Host workbox
  HostName server.example.com
  User you
  Port 2222
```

Then attach with:

```bash
shepherd --remote workbox
```

Remote attach supports Linux and macOS hosts on x86_64 and aarch64. Shepherd checks the remote platform and known install paths for a peer with the same Shepherd version and protocol. If none exists, an interactive attach can offer to run the peer-native `shepherd-install`; non-interactive runs fail with the same instruction instead of modifying the host. The peer must already provision that installer, which performs a host-local native build.

Native Windows `shepherd --remote` is not part of the Windows beta. From Windows, SSH into the server and run `shepherd` there.

By default, `shepherd --remote` runs remote setup and the bridge through a temporary SSH config that includes your SSH config first, then adds fallback keepalive settings and a private per-attach control socket for connection reuse. Existing user keepalive settings win. Set `[remote].manage_ssh_config = false` to use plain `ssh` without Shepherd's generated config or control socket.

Remote attach uses your normal OpenSSH authentication. If the target uses a passphrase-protected key in a non-interactive shell, script, CI job, or mobile terminal that cannot show the passphrase prompt, load the key into ssh-agent first:

```bash
ssh-add
shepherd --remote workbox
```

For any remote authentication failure, verify plain SSH access first with `ssh workbox`, then run `shepherd --remote workbox` again.

By default, remote attach uses the normal restart/stop flow if it needs to replace or restart a running remote server. To opt into experimental live handoff for a supported running remote server, pass `--handoff`:

```bash
shepherd --remote workbox --handoff
```

If you SSH into the server first and run `shepherd` there, Shepherd runs entirely on the server. That mode is useful and simple, but it cannot access your local desktop clipboard beyond normal terminal text paste.

Shepherd never streams the local binary to the peer and never downloads a legacy upstream release as a fallback. When the peer is missing or incompatible, run `shepherd-install` there—or accept the interactive offer to invoke it—then retry the attach.

## Remote named sessions

Use `--session` with `--remote` to attach to a named session on the remote host:

```bash
shepherd --remote workbox --session agents
```

## Direct terminal attach

Full Shepherd attach opens the whole workspace UI. Direct attach opens one server-owned terminal in your current terminal.

Direct terminal attach is Unix-only in the Windows beta.

Attach by agent target:

```bash
shepherd agent attach reviewer
```

Attach by terminal ID:

```bash
shepherd terminal attach term_abc123
```

Direct attach streams the current rendered terminal state, then live ANSI frames. Input goes straight to that terminal.

Detach with `ctrl+b q`. Send a literal `ctrl+b` with `ctrl+b ctrl+b`.

Only one writable direct attach client owns input and resize for a terminal. Use `--takeover` to replace an existing owner:

```bash
shepherd terminal attach term_abc123 --takeover
```

For third-party bridges that only need rendered terminal bytes, use a read-only
terminal session observer:

```bash
shepherd terminal session observe w1:p1 --cols 120 --rows 40
```

It prints newline-delimited JSON `terminal.frame` records with base64 ANSI
bytes, then a `terminal.closed` record when the server closes the stream.
Multiple observers can watch the same terminal without taking input, resize,
scroll, or takeover ownership.

For an interactive bridge, use a writable terminal session controller:

```bash
shepherd terminal session control w1:p1 --takeover --cols 120 --rows 40
```

Control mode prints the same newline-delimited frame records and reads
newline-delimited JSON commands on stdin. `terminal.input` sends text or
base64 bytes, `terminal.resize` changes the controller viewport,
`terminal.scroll` scrolls the attached viewport, and `terminal.release` closes
the controller. Only one controller owns input and resize at a time.

## Single-process escape hatch

Use `--no-session` to run Shepherd without the background server/client split:

```bash
shepherd --no-session
```

This is mainly an escape hatch for debugging or compatibility. The default persistent session mode is the normal path.
